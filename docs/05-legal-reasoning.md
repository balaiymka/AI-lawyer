## 1. Аудит: где система ошибалась (диагностика)

### Как было устроено

```text
вопрос → нормализатор (Gemini) → 3–8 поисковых формулировок
       → гибридный поиск (BGE-M3 dense + sparse, RRF) → реранкер → top-8 пунктов
       → (отсылки в другие акты: xrefs.py) → <context> → Gemini → проверка цитат (verify.py)
```

- **Чанкинг.** Единица чанка — юридическая единица, а не окно токенов (`app/services/rag/chunker.py`):
  - пункт статьи вместе с подпунктами;
  - для длинных перечней — каждый подпункт с вводной фразой;
  - в начале чанка «хлебные крошки» (акт › глава › статья › пункт).

  Структура (раздел → глава → статья → пункт → подпункт) уже хранится в `legal_units` через `parent_id`, вместе
  с редакциями (`act_versions`, `valid_from` / `valid_to`). Это хорошая основа, переписывать её не нужно.
- **Контекст для Gemini** — плоский список из 8 фрагментов (`app/services/lawyer/context.py`).

### Проблема 1: потеря вопросов при retrieval

- Все вопросы сообщения искались **одним** поиском и одной формулировкой реранкера. Реранкер ранжирует
  кандидатов по близости ко всему сообщению, и одна тема (голосование) занимала все 8 мест.
- Нормы про взносы, общее имущество и выдачу протокола в контекст не попадали. Gemini отвечал по ним
  «по памяти» или пропускал вопрос.
- Пример ментора: вопрос «председатель + тариф + антенна + составь вопросы» получал только нормы о голосовании.

### Проблема 2: взаимосвязанные нормы читались по отдельности

П. 8 ст. 42 ЗРК «О жилищных отношениях» устроен так:

> Решение принимается большинством от участников голосования, **за исключением вопросов, указанных в
> подпунктах 6)–16) и 21) пункта 5**, по которым — большинством от общего числа собственников.

Правило лежит в п. 8, а перечень, к которому оно относится, — в п. 5. В выдачу попадал один из этих фрагментов,
поэтому модель не могла определить:
- что тариф (пп. 7) требует 51 голос **от всех 100** собственников;
- что председатель (пп. 3) избирается большинством **от участников**.

Связей между пунктами в базе не было. `xrefs.py` разбирал только отсылки в другие акты («статьи 917
Гражданского кодекса»), а отсылки внутри статьи («пункта 5 настоящей статьи») не разбирал.

### Проблема 3: ответ не проверялся по существу

- `verify.py` проверяет только формальную сторону: что chunk_id есть в контексте и что цитата дословная.
- Числа, пороги, применение исключений и полнота ответа не проверялись.

## 2. Архитектура после изменений

```text
сообщение
  │
  ▼
[1] Нормализатор (Gemini, без мышления)
      язык, факты, дата события, sub_questions: [{question, kind: legal|calculation|drafting, search_queries}]
  │
  ▼  для КАЖДОГО подвопроса — своя ветка (одиночный вопрос = одна ветка)
[2] Initial Retrieval        dense + sparse + точные ссылки → RRF → реранкер (своя формулировка ветки)
[3] Dependency Expansion     граф закона legal_refs: исключения, условия, процедуры, перечни (в обе стороны)
                             + отсылки в другие акты (xrefs.py) с учётом редакции на дату события
[4] Branch Reasoning         Gemini разбирает ветку: правило с исключениями, расчёт, текст; missing → follow_up_queries
[5] Follow-up Retrieval      если ветке не хватило нормы — дополнительный поиск и повторный разбор (≤ 1 раз)
  │
  ▼
[6] Evidence Consolidation   контекст = нормы всех веток по очереди (ветки не смешиваются в общий top-8);
                             у каждой ветки сохраняется свой список источников (analysis.branches[].sources)
[7] Legal Reasoning          итоговый ответ из <context> + <branch_analyses>:
                             вывод, расчёты, готовые тексты, «на что ещё обратить внимание», план действий
[8] Verification             второй юрист сверяет ответ с нормами →
                             не хватает нормы? → дополнительный поиск → исправление → повторная проверка (≤ 2 раз)
[9] verify.py                chunk_id только из контекста, цитаты дословно, статьи вне контекста → needs_review
```

| Компонент | Файл |
|---|---|
| Подвопросы | `app/services/nlu/normalizer.py`, `app/prompts/normalizer.md` |
| Ветки, допоиск, сборка | `app/services/lawyer/pipeline.py` (`_branch_request`, `_analyze_branches`, `_merge`) |
| Разбор ветки | `app/services/lawyer/analysis.py`, `app/prompts/branch.md` |
| Граф закона: разбор | `app/services/rag/law_graph.py` |
| Граф закона: хранение и поиск | `app/services/rag/graph.py`, таблица `legal_refs` (миграция `0003`) |
| Фактчек | `app/services/lawyer/analysis.py` (`fact_check`), `app/prompts/factcheck.md` |
| Формат ответа | `app/services/lawyer/schema.py`: `calculations`, `drafts`, `attention` |
| Интерфейс | `apps/web/components/chat/AnswerCard.tsx`: расчёты, готовый текст, «обратите внимание», отметка фактчека |

### Граф закона (Legal Graph RAG)

- **Как строится.** При загрузке закона разбираются явные отсылки на номер пункта или статьи внутри акта:
  - «подпунктах 6)–16) и 21) пункта 5 настоящей статьи» (с диапазонами);
  - «пунктом 3 настоящей статьи», «подпунктами 1) и 2) настоящего пункта», «частью третьей настоящей статьи»;
  - «пунктах 1 и 2 статьи 346 настоящего Кодекса», «пунктом 5 настоящих Правил».
- **Тип связи** определяется по формулировке в той же фразе:

| kind | Формулировки | Сколько в базе |
|---|---|---|
| exception | «за исключением», «кроме», «если иное не предусмотрено», «не распространяется» | 508 |
| condition | «в случаях, установленных…», «при условии», «с учётом требований», «при наличии» | 143 |
| procedure | «в порядке, установленном…», «по правилам» | 52 |
| reference | «в соответствии со статьёй…» и прочие | 4 384 |

- **Подтверждение в тексте.** Связь заносится, только если в тексте есть отсылка на конкретный номер.
  Поэтому у каждой связи есть подтверждение в законе, и никаких «семантических догадок» в графе нет.
- **Редакции.** Рёбра строятся внутри одной редакции (`version_id`), поэтому нормы разных редакций не
  смешиваются. Отсылки в другие акты подтягиваются во время поиска уже в редакции на дату события.
- **Поиск по графу** работает в обе стороны:
  - нашёлся п. 8 → добавляется перечень п. 5;
  - нашёлся пп. 7) (взносы) → добавляется п. 8 (исключение для него);
  - нашёлся пп. 3) (председатель) → добавляется п. 8 как общее правило для всего перечня (`rule_for_list`).

  Приоритет: исключения → условия → правило перечня → процедура → отсылки. Не больше 5 пунктов на ветку.
- **В контексте у Gemini** связанные пункты помечены `role="linked_norm"`, с типом связи и пунктом, к которому
  они относятся. Промпт требует определить, общее правило или исключение, и назвать подпункт.

### Голосование ОСИ (основной тестовый сценарий)

Это не подсказка под конкретный вопрос, а общие правила чтения норм о голосовании, которые заложены в промптах
веток, итогового ответа и фактчека:

- различать **кворум** (участие более половины от общего числа), **базу расчёта** (все собственники или
  участники голосования) и **требуемое большинство** для конкретного вида решения;
- не применять «50% + 1» автоматически: найти норму и определить по перечню п. 5, исключение это или общее
  правило;
- при числах пользователя считать конкретно. «Большинство» от N — это целая часть N/2 плюс один. Если неизвестно,
  сколько придёт, считать для минимального кворума и показать, как меняется результат;
- не хватает факта (например, общего числа собственников) — задать только этот вопрос и дать вывод для
  вероятного варианта.

Пример «100 собственников, участвовали 60, за председателя 35»:
- кворум есть: 60 > 50;
- пп. 3) — общее правило, нужно большинство от участников: 31 из 60;
- 35 ≥ 31, решение принято.

Тот же расклад для тарифа (пп. 7), 45 голосов «за»: тариф — исключение, нужно большинство от всех: 51 из 100;
45 < 51, решение **не** принято.

### Проактивный советник и стиль

- **Поле `attention`** («На что ещё важно обратить внимание», 1–4 пункта). Это существенное, о чём пользователь
  не спросил: как принималось решение, соблюдена ли процедура, какие документы запросить, есть ли основания
  оспорить, какие риски у самого пользователя. Каждый пункт опирается на норму (citations) или на факт из
  сообщения. Фактчек отдельно проверяет, что предупреждения не выдуманы.
- **Стиль.** Вместо «обратитесь в компетентный орган» — конкретные шаги: что запросить, что проверить, куда
  идти. Если сценариев несколько, каждый разбирается отдельно. Фактчек отмечает общие формулировки как ошибку.

## 4. Специализированные Legal AI модели (Hugging Face)

Сейчас используются:
- BGE-M3 (эмбеддинги dense + sparse, ru + kk);
- bge-reranker-v2-m3;
- Gemini Flash для рассуждений.

| Задача | Кандидаты | Оценка для законов РК |
|---|---|---|
| Семантический поиск по законам | `irinaqqq/lexir` (sentence-transformers, юридический поиск ru + kk) | ближе всего по задаче; данных мало (около 3,8 тыс. пар), качество и лицензию нужно проверить на нашем наборе |
| | `ai-forever/ru-en-RoSBERTa`, Giga-Embeddings-instruct | сильные русские эмбеддеры (ruMTEB), но не юридические и без казахского |
| | `shyngys879/kazakh-e5-rag-embedding`, `Tim2190/granite-278m-kk` | казахские эмбеддеры для RAG, не юридические |
| Юридическая языковая модель (основа для дообучения) | `TryDotAtwo/RuModernBERT-ruLaw` | русское право (РФ); как основа для своего ретривера или классификатора — после дообучения на РК |
| Не подходят | `legal-bge-m3` и подобные модели на праве США / ЕС | обучены на английском, термины и структура другие |

**Вывод.** Готовой модели «для законов РК на русском и казахском» нет. Юридическая логика (исключения, базы
расчёта, перечни) у нас держится на графе и на Gemini, и это сильнее любой маленькой модели. Специализированные
модели имеет смысл пробовать в узких местах: поиск и реранкинг по формулировкам людей, классификация положений.

**Эксперименты (по порядку)**

1. **Реранкер.** Сравнить bge-reranker-v2-m3 с дообученным на наших парах. Переиндексация не нужна, сравнение
   дешёвое. Метрики: recall@8, MRR на `retrieval_gold.jsonl` (ru, kk, шала-қазақша, латиница, опечатки).
2. **Эмбеддеры.** lexir, RoSBERTa, kazakh-e5 против BGE-M3 на **копии** коллекции Qdrant.
   - Метрики: recall@20 до реранкера, отдельно по стилю вопроса.
   - Цена: переиндексация ~43 тыс. фрагментов, на CPU сервера это часы.
3. **Дообучение своего эмбеддера.** Пары «вопрос → правильный пункт» из золотого набора и из диалогов, которые
   юрист отметил верными, плюс hard negatives из соседних пунктов той же статьи.
4. **Классификатор связей** (exception / condition / procedure) против текущих правил-регулярок. Метрики:
   precision и recall на 200 размеченных вручную отсылках.

Модель меняем, только если на нашем наборе метрика выросла, а на казахских вопросах не упала.

## 5. Qdrant и альтернативы

| | Qdrant (сейчас) | pgvector | Weaviate | Milvus | OpenSearch |
|---|---|---|---|---|---|
| Dense + sparse в одном запросе | да (named vectors, fusion) | dense; sparse — отдельно через tsvector или sparsevec | да (hybrid BM25 + vector) | да | да (BM25 + kNN) |
| Фильтры по метаданным (редакция, дата, акт) | быстрые, payload-индексы | SQL, удобно | да | да | да |
| Связь с графом норм | граф в PostgreSQL, связка по `unit_id` | граф и векторы в одной БД, JOIN | ссылки между объектами | нет | нет |
| Ресурсы на ВМ 2 vCPU / 8 ГБ | ~1 ГБ, один контейнер | 0 (уже есть PostgreSQL) | средне | тяжёлый (etcd, MinIO) | тяжёлый (JVM, ≥ 2–4 ГБ) |
| Эксплуатация в Yandex Cloud | Docker на ВМ | Managed PostgreSQL (pgvector есть) | Docker | Docker / k8s | Managed OpenSearch (дорого) |
| Масштаб | миллионы векторов на одной ноде | до миллионов, медленнее при фильтрах | миллионы | миллиарды | миллионы |

**Когда Qdrant действительно лучше.** Нужен гибридный поиск dense + sparse от BGE-M3 одним запросом с жёсткими
фильтрами по дате редакции. У нас ровно этот случай, и Qdrant лёгкий для нашей ВМ.

**Когда замена ничего не даст.** На нашем объёме (~43 тыс. фрагментов, станет ~100–200 тыс. с судебной практикой)
все варианты отвечают за миллисекунды. Время ответа уходит на реранкер на CPU (~30 с) и на Gemini, а не на
векторную базу. Ошибки, найденные в аудите, вызваны логикой поиска (один top-8, плоское чтение норм), а не базой.

**Единственная разумная альтернатива — pgvector.** Векторы и граф были бы в одной БД, Managed PostgreSQL в
Yandex Cloud. Минус: гибридный sparse-поиск и fusion пришлось бы писать вручную. Миграция оправдана, только если
появится измеримая проблема, например нужно делать JOIN графа и векторов одним запросом. Сейчас её нет, и
миграцию мы **не предлагаем**.

## 6. Архитектура для судебной практики (этап 5)

Судебная практика хранится **отдельно** от законодательства и никогда не смешивается с нормами в одном
контексте без пометки.

```text
PostgreSQL                                         Qdrant
court_cases                                        коллекция court_chunks (отдельно от legal_chunks)
  id, court, instance, case_number, decided_at,      payload: case_id, section (facts|claims|arguments|
  status (вступило в силу / отменено / обжалуется),           reasoning|decision), dispute_type, court,
  dispute_type (голосование ОСИ, взносы, затопление…),        decided_at, outcome, status
  outcome (удовлетворено / отказано / частично),
  source_url, anonymized: bool
court_case_sections   (факты, требования, доводы сторон, мотивировка, резолютивная часть)
court_case_norms      case_id → legal_units.id     ← связь с графом законов: какие нормы применил суд
```

- **Загрузка.** Выгрузка решений (источник и условия использования нужно согласовать) → обезличивание →
  разбивка на разделы → извлечение применённых норм. Ссылки на статьи распознаются тем же `refs.py`, затем
  связываются с `legal_units` в редакции на дату решения.
- **Поиск.** Отдельная ветка `practice`. Запускается, только когда вопрос касается спора или риска оспаривания.
  Ищем по разделу «факты» (похожая ситуация) и фильтруем по `dispute_type` и статусу.
- **Ответ.** Отдельный блок «Судебная практика»:
  - решение помечено судом, датой и статусом;
  - формулировка всегда «в похожем деле суд …», а не «закон требует»;
  - отменённые решения не используются как поддержка позиции;
  - одно решение никогда не подаётся как обязательное правило.
- **Фактчек** дополнительно проверяет, что выводы из практики не выданы за норму закона.

## 7. Тестовый набор и метрики

`apps/api/tests/eval/complex_questions.jsonl` содержит 17 вопросов. Категории из ТЗ:

| Категория | Вопросы |
|---|---|
| простой вопрос | s01 |
| несколько независимых вопросов | m01, c06, c07, c08, z01 (пример из ТЗ: 4 задачи) |
| связанные вопросы | c09 (казахский), m02 |
| исключение из общего правила | c04, c05, c10, v02 |
| расчёт голосов | m01, m02, c03, v01, v02 |
| несколько статей | c03 |
| тарифы и процедура утверждения | m02, t01 |
| недостаточно данных | n01 (ожидается уточняющий вопрос) |
| составить документ | m01, m02, c10, z01 |
| скрытый риск | r01 (ожидается блок «обратите внимание») |

**Автоматические проверки** (`python -m tests.eval.run_answer_eval --api https://…/backend`):

| Проверка | Что значит |
|---|---|
| нормы найдены | нужные пункты попали в контекст |
| числа верны | ключевые цифры (кворум, голоса) есть в ответе |
| готовый текст | если просили составить — текст есть |
| вопрос разбит | число подвопросов не меньше ожидаемого |
| вывод | вердикт (yes / no / depends) совпадает с эталоном |
| риски | есть блок «обратите внимание» |
| уточнение | при нехватке данных задан уточняющий вопрос |

Плюс в отчёте: время ответа и сколько раз фактчек исправил ответ.

**Экспертная проверка.** У каждого вопроса есть эталонный разбор (поле `note`). Полные ответы сохраняются в
`tests/eval/reports/answers-*.json`. Юрист оценивает ответы по шкале 0–2 по пунктам ТЗ:
- полнота;
- точность выводов;
- ссылки;
- исключения;
- расчёты;
- практичность рекомендаций;
- выявление рисков.

Сначала юрист проверяет все сложные вопросы (исключения, расчёты, скрытый риск).

### Результаты прогона 23.11.2026 (сервер, Gemini Flash)

- **Полный прогон 17 вопросов.** 14 из первых 14 прошли все проверки, кроме казахского c09: в одном прогоне не
  нашлись нормы о голосовании, при повторе он прошёл. На r01 прогон оборвался: завис запрос к Gemini. Добавлен
  таймаут 120 с на запрос (`GEMINI_TIMEOUT_SEC`).
- **Повтор r01, n01, z01, c09.** 4 из 4 по всем проверкам. Риски найдены (r01), при нехватке данных задан
  уточняющий вопрос (n01), пример из ТЗ разбит на 3 подвопроса с готовым заявлением (z01).
- **Время ответа** 52–128 с (в среднем ~80 с).
- **Риск — нестабильность.** Gemini формулирует подвопросы и поисковые запросы немного по-разному от прогона к
  прогону, поэтому отдельный вопрос иногда проваливается. Прогон нужно делать целиком и смотреть на долю
  прошедших, а не на один вопрос. Набор стоит расширять вопросами с плавающим результатом.
