Вопрос 2

Что работает по API, а что на нашем сервере

свой сервер

  • BGE-M3 и реранкер — загружены прямо в процесс API, работают на CPU, GPU не нужен.
  • Qdrant — векторная база (не модель), отдельный процесс.
  • PostgreSQL, сайт Next.js, Playwright для загрузки законов.

Почему так: модели небольшие, работают на обычном процессоре, за каждый вопрос не платим, тексты вопросов на поиске не уходят наружу. Качество на казахском и шала проверено на 186 контрольных вопросах.

по API

  • Языковая модель — разбор вопроса и ответ юриста.

Почему так: модель уровня Claude или Gemini Pro у себя требует нескольких GPU по 80 ГБ — это дороже API при нашем объёме (подробно в вопросе 9). Код сделан так, что провайдера можно сменить настройкой LLM_PROVIDER.

Как сейчас в демо. Ответ пишет Claude через личную подписку разработчика (Claude Code) — только для разработки и демо; для публичного сайта нужен API-ключ. В этом режиме разбор вопроса делается без LLM, по словарю и правилам (запасной путь), чтобы не тратить лишние 10–20 секунд.
Вопрос 3

Цепочка обработки вопроса: что происходит по шагам

Пример: житель пишет «соседи сверху затопили квартиру, что делать». Всё ниже выполняет одна функция run_chat в app/services/lawyer/pipeline.py. Ответ отдаётся потоком (SSE): житель видит этапы «понимаю вопрос → ищу нормы → пишу ответ» и найденные нормы ещё до готового ответа.

1
Вопрос уходит с сайта на серверкод

Сайт (Next.js) отправляет POST /v1/chat с текстом, ролью (житель / юрист) и историей дела. Сервер держит соединение открытым и раз в 15 секунд шлёт служебный «пинг», чтобы соединение не обрывалось, пока модель думает.

Файлы: apps/web/components/chat/ChatView.tsx, app/routers/chat.py
2
Разбор вопросаLLM по APIзапасной путь — код

LLM по инструкции prompts/normalizer.md возвращает строгий JSON: язык вопроса и ответа, вопрос юридическим языком на ru и kk, категорию, стороны, факты, упомянутые нормы («ст. 42 п. 8»), дату события и 2–6 поисковых формулировок. Если API недоступен — тот же результат собирает код: определяет язык по буквам и словам, переводит латиницу в кириллицу («kvorum» → «кворум»), добавляет термины из словаря сленга ЖКХ, ищет даты регулярными выражениями.

Токены: ~2 000 вход · ~500 выходВремя: 2–5 с (LLM) или <10 мс (код)Файлы: app/services/nlu/*
3
Подготовка поискового запроса и выбор редакциикод

Собираем до 8 формулировок для поиска. Явные ссылки на нормы («ст. 42 п. 8 ЗЖО») разбираем регулярными выражениями — их найдём точно, без модели. Если в вопросе есть дата события («затопили в марте 2022»), выбираем для каждого акта редакцию, действовавшую в тот день.

Файлы: normalizer.to_search_request, app/services/rag/refs.py, app/services/lawyer/editions.py
4
Векторы вопросаBGE-M3 · свой сервер

Каждую формулировку BGE-M3 переводит в два вектора: смысловой (1024 числа) и словесный (веса слов). Это та же модель, которой векторизованы законы, — иначе векторы были бы несравнимы.

Время: 0,2–0,7 сПамять: ~1,2 ГБ (модель уже в памяти)
5
Поиск в QdrantQdrantкод

Три канала параллельно: поиск по смыслу, поиск по словам и точные попадания по явным ссылкам из шага 3 (они закрепляются наверху). Фильтры: язык, действующая редакция или редакция на дату события. Списки объединяются методом RRF (Reciprocal Rank Fusion). Нормы Кодекса и Закона получают приоритет над Правилами и приказами.

Время: 0,2–0,9 сБаза: 42 780 фрагментовФайлы: app/services/rag/retriever.py, vector_store.py
6
Переранжированиереранкер · свой сервер

20 лучших кандидатов реранкер читает вместе с вопросом и заново оценивает. Затем код убирает повторы (не больше 2 фрагментов одного пункта и 3 одной статьи) и оставляет 8 лучших. Если в найденной норме написано «в соответствии со статьёй 10», код подтягивает и статью 10 — до 4 таких отсылок.

Время: ~2 с на CPU (0,2–0,3 с на GPU)Память: ~1,2 ГБНужная норма первой: 65% без реранкера → 67% с ним (с приоритетом закона)
7
Сборка контекста для моделикод

Тексты 8–12 пунктов берутся из базы и оборачиваются в XML: у каждого — номер, акт, статья, пункт, уровень акта (Кодекс / Закон / Правила), редакция, ссылка на Adilet. Эти же нормы сразу показываются жителю в панели «Источники».

Объём: 4–12 тыс. знаков ≈ 1,5–4 тыс. токеновФайл: app/services/lawyer/context.py
8
Ответ юристаLLM по API

LLM получает инструкцию юриста (prompts/lawyer.md: отвечать только по нормам из контекста, ссылаться на номер нормы, цитировать дословно) плюс контекст, результат разбора, вопрос и историю дела. Возвращает JSON по строгой схеме: вердикт, простой ответ для жителя, ответ для юриста, план действий, правовые основания с цитатами, уточняющие вопросы. Текст идёт потоком.

Токены: ~8 000 вход · ~5 000 ответ + рассуждения моделиВремя: 11–45 сФайл: app/services/lawyer/generator.py
9
Проверка ссылоккод

Модели не верим на слово. Ссылка на норму, которой нет в контексте, удаляется. Номер статьи и название акта берутся из базы, а не из текста модели. Цитата должна дословно совпадать с текстом пункта — иначе подставляется настоящий текст и ставится отметка «цитата не подтверждена». Статьи, упомянутые без опоры на контекст, помечают ответ «нужна проверка юристом».

Время: миллисекундыФайл: app/services/lawyer/verify.py
10
Сохранение и показPostgreSQL

В базу пишутся вопрос, результат разбора, ответ, процитированные нормы, расход токенов и время каждого этапа, а также след поиска (какие кандидаты были). Житель видит ответ, источники со ссылками на Adilet и редакцию, по которой дан ответ. Ответы с отметкой «нужна проверка» попадают юристу в админку.

Файл: app/services/lawyer/store.pyИтого вопрос: ~15–50 с, из них поиск ~3 с
Вопрос 4

Загрузка, разбор, индексация и обновление законов

Запускается из админки кнопкой (или командой python -m ingest). Задача идёт в фоне, админка показывает журнал. Из шести шагов модель работает только на одном — векторизации.

1
Список актовчеловек + конфиг

Файл ingest/sources.toml: код акта (ZHO, GK_GEN…), номер на Adilet, название, уровень в иерархии. Сейчас 15 актов. Новый акт добавляется одной записью или из админки.

2
Скачивание с Adiletкод · Playwright

adilet.zan.kz — одностраничное приложение: обычный HTTP-запрос возвращает пустую страницу, текст появляется после выполнения JavaScript. Поэтому страницу открывает headless-браузер Chromium (Playwright), как обычный посетитель, и сохраняет только блок с текстом акта. Отдельно на русском и казахском. Бережно к сайту: один запрос за раз, пауза между запросами, кэш на диске.

Файл: ingest/adilet/fetcher.py
3
Хронология редакцийкод

Со вкладки «История» Adilet получаем список всех редакций с датами начала действия. Каждая редакция — отдельный документ на Adilet, она скачивается так же, как в шаге 2.

Файл: ingest/adilet/versions.py
4
Разбор на структурукод · BeautifulSoup + регулярные выражения

На странице текст лежит плоским списком абзацев. Код восстанавливает дерево по тексту: раздел → глава → параграф → статья → пункт → подпункт (в русской версии статьи — заголовки, в казахской — «NN-бап»). У каждой единицы путь вида art42/p3/sp1, одинаковый для ru и kk, — по нему языки склеиваются в одну запись. Сноски «в редакции Закона РК от …» сохраняются отдельно.

Файл: ingest/adilet/parser.py
5
Запись редакции в PostgreSQLPostgreSQL

Считаем хэш SHA-256 исходного текста (ru + kk). Если такой уже есть — ничего не меняется. Если текст новый — создаётся новая редакция с датой начала действия, она становится действующей, а старая остаётся в базе.

Файл: ingest/loader.py
6
Нарезка и векторизациякодBGE-M3Qdrant

Фрагмент поиска — это юридическая единица, а не кусок в N слов: пункт со своими подпунктами, текст статьи без пунктов, а у длинных пунктов (больше 1500 знаков) ещё и каждый подпункт отдельно. В начале фрагмента «хлебные крошки» (акт › глава › статья › пункт), чтобы модель знала, откуда кусок. Утратившие силу пункты не индексируются. BGE-M3 векторизует фрагменты пачками по 8; если текст пункта не изменился между редакциями, вектор берётся готовый (по хэшу), а не считается заново. Векторы и метки (акт, статья, пункт, язык, срок действия редакции) пишутся в Qdrant.

Вся база: 42 780 фрагментов, ≈1 ч на ноутбукеНовая редакция: минуты (считаются только изменённые)Файлы: app/services/rag/chunker.py, ingest/indexer.py

Вопрос 5

Вопрос 6

Что хранится в PostgreSQL, а что в других местах

PostgreSQL — главная база, не только законы. Векторов в ней нет: они в Qdrant. Размер базы сейчас 138 МБ, из них 129 МБ — тексты законов.

Законодательство

legal_acts · act_versions · legal_units · legal_chunks · legal_glossary
  • акты и их уровень (Конституция, кодекс, закон, приказ)
  • редакции с датами начала и конца действия, хэш текста
  • статьи, пункты, подпункты на ru и kk, сноски
  • фрагменты для поиска (тексты, без векторов)
  • словарь терминов и сленга ЖКХ

Пользователи и объекты

users · buildings · premises
  • аккаунты и роли: житель, юрист, админ
  • дома и помещения

Дела и история запросов

cases · messages · message_citations · retrieval_traces
  • дела (переписка по одной ситуации)
  • вопросы, результат разбора, ответы
  • какие нормы процитированы
  • расход токенов, время этапов, след поиска

Документы

doc_templates · document_drafts · generated_documents · uploaded_files
  • шаблоны заявлений и исков
  • черновики, которые житель заполняет в чате
  • сведения о загруженных файлах (сами файлы — на диске)

Проверка юристом и служебное

reviews · review_findings · reference_rates · calculations · audit_log
  • замечания юриста к ответам
  • МРП, ставки для калькуляторов пени
  • расчёты
  • журнал действий

Вне PostgreSQL

  • Qdrant — векторы фрагментов (смысловой + словесный) и метки для фильтров. ~600 МБ на диске.
  • Диск — файлы к документам: сканы, фото. В модели не отправляются.
  • Веса моделей — BGE-M3 и реранкер, ~6 ГБ файлов, в памяти ~2,3 ГБ.

Вопрос 9

Свои модели или готовые API: что выгоднее нам

МодельРешениеПочему
BGE-M3у себя+ маленькая, работает на CPU, бесплатна на любом объёме, база уже проиндексирована, проверена на kk и шала. − держит ~1,2 ГБ памяти.
Реранкеру себя+ поднимает точность первого места с 65% до 67%, а вместе с приоритетом закона — с 58% до 67%; бесплатен. − ~2 с на CPU. Можно отключить на самом дешёвом сервере.
LLM для ответаAPIСвоя модель уровня Claude / Gemini Pro (70B+) требует 2 GPU по 80 ГБ — сервер с такими GPU стоит в десятки раз дороже нашего счёта за API при объёме до нескольких тысяч вопросов в месяц. Маленькие открытые модели (7–8B, KazLLM, Sherkala) помещаются на одну GPU, но заметно слабее в юридических рассуждениях и строгом JSON; у KazLLM ещё и лицензия только для некоммерческого использования.
LLM для разбора вопросаAPI, дешёвая модельЗадача простая: Haiku / Flash стоит доли цента за вопрос. Запасной разбор без LLM уже есть в коде.
Вывод. Маленькие модели поиска держим у себя на обычном сервере без GPU (4 vCPU, 8 ГБ). Языковую модель берём по API и платим за вопросы: при нашем объёме это в разы дешевле своего GPU-сервера. Свою LLM имеет смысл пересматривать только при десятках тысяч вопросов в месяц или если по закону о персональных данных тексты вопросов нельзя будет отправлять во внешний сервис.
