## 1. Тема, язык, ключевые термины и дата события

**Функция-вход:** `normalize(text)` — `app/services/nlu/normalizer.py:186-194`.

```python
if s.llm_provider == "anthropic" and s.anthropic_api_key:
    try:
        return await normalize_llm(text)
    except Exception as exc:
        log.warning("LLM normalizer failed, falling back to heuristic: %s", exc)
return normalize_heuristic(text)
```

### Путь А — LLM (только при `LLM_PROVIDER=anthropic` и ключе)

`normalize_llm` — `normalizer.py:94-121`.
- Модель `settings.llm_model` (`claude-opus-5-5`), `max_tokens=4000`, `effort: "low"`.
- Ответ строго по JSON-схеме `NORMALIZER_SCHEMA` (`normalizer.py:60-82`), structured outputs.
- Системный промпт — файл `app/prompts/normalizer.md` (36 строк). Суть:
  - «Ты — лингвистический препроцессор… Ты НЕ отвечаешь на вопрос пользователя»;
  - словарь сленга: «кск», «оси», «капиталка», «су басты» → термины;
  - 7 действий: определить язык `kk/ru/mixed` и `reply_lang`; переписать запрос на ru и kk; определить стороны из фиксированного списка ролей; определить категорию из 15 (`flooding`, `roof_leak`, `osi_governance`, `fees_and_debts`, `tariffs_monopoly`… `other`); извлечь явно упомянутые нормы; составить 3–5 поисковых подзапросов на ru и 1–2 на kk юридическими терминами; задать до 3 уточняющих вопросов;
  - правило даты: `event_date` в формате ГГГГ-ММ-ДД; только год → 1 июля; месяц и год → 15-е; текущая ситуация → пусто; даты реквизитов актов («Закон от 16 апреля 1997 года») не считаются.
- Вопрос передаётся как `<user_message>\n{text}\n</user_message>`.

**Формат результата** — `NormalizedQuery` (`normalizer.py:41-54`):

```
detected_lang: kk | ru | mixed      reply_lang: kk | ru
normalized_ru, normalized_kk: str   category: str
parties: [{role, description}]      facts: [str]
mentioned_norms: [str]              search_queries: [{lang, q}]
clarifying_questions: [str]         event_date: "ГГГГ-ММ-ДД" | ""
event_date_precision: day|month|year source: llm | heuristic
```

### Путь Б — без LLM (работает сейчас в демо)

`normalize_heuristic` — `normalizer.py:165-184`:
1. Латиница → кириллица, если текст в основном латиницей (`translit.py`).
2. Язык: `detect_lang` (`normalizer.py:153-163`). Считает казахские буквы `әғқңөұүһі` и казахские слова (×2) против русских служебных слов. Если есть оба — `mixed`; язык ответа — kk, если казахских признаков не меньше.
3. Термины: `expand_query` (`app/services/nlu/glossary.py:87-93`) — регулярные выражения словаря сленга добавляют юридические термины.
4. Поисковые запросы: исходный текст, транслит (если был) и «текст + термины».
5. `category="other"` — тему этот путь **не определяет**.

### Дата события — в обоих путях

`_with_event_date` (`normalizer.py:124-136`): берёт дату от LLM, если она корректна; иначе `extract_event_date` (`app/services/nlu/event_date.py:52-86`) — регулярные выражения:
- `ДД.ММ.ГГГГ` → точность `day`;
- «март 2022», «2022 жылғы наурыз» → 15-е число, `month`;
- «в 2022 году», «2022 жыл» → 1 июля, `year`;
- даты после «от / редакции / №» пропускаются (это реквизиты);
- даты раньше 1997 и в будущем отбрасываются;
- выбирается самая точная; год, равный текущему, игнорируется (значит действующая редакция).

## 2. Как BGE-M3 считает dense и sparse, что уходит в Qdrant

**Код:** класс `BGEM3`, `app/services/rag/models.py:47-85`.

- Один прогон модели `BAAI/bge-m3` даёт `last_hidden_state`.
- **Dense:** вектор CLS-токена `hidden[:, 0]`, L2-нормализован, 1024 числа (`models.py:74`).
- **Sparse:** `relu(sparse_linear(hidden))` — вес каждого токена. Веса `sparse_linear` загружаются из `sparse_linear.pt` модели. Служебные токены (CLS, EOS, PAD, UNK) и нулевые веса отбрасываются; для повторяющегося токена берётся максимальный вес. Результат — словарь `{id токена: вес}` (`models.py:75-84`).
- Длина: при индексации законов — до 1024 токенов (`ingest/indexer.py:81`), для вопросов — до 256 (`retriever.py:123`).
- Устройство и точность: MPS или CUDA → fp16; CPU → fp32 (`models.py:24-44`).

**Что индексируется** — фрагмент = юридическая единица, а не окно в N токенов (`app/services/rag/chunker.py`, описание в строках 1-12):
- пункт со своими подпунктами;
- подпункт прямо под статьёй;
- собственный текст статьи;
- у пунктов длиннее 1500 знаков — ещё и каждый подпункт с вводной фразой;
- текст начинается с «хлебных крошек»: акт › глава › статья › пункт;
- утратившие силу единицы не индексируются.

**Что пишется в Qdrant** — `ingest/indexer.py:91-107`. Коллекция `legal_chunks`, id точки = id фрагмента в PostgreSQL.
- Векторы: `dense` (1024, косинус) и `sparse`.
- Payload: `chunk_id, unit_id, act_code, lang, path, article, point, kind, breadcrumb, content` (полный текст), `content_sha, version_id, valid_from, valid_to, valid_from_i, valid_to_i` (даты числом ГГГГММДД), `is_current, temporal` (у акта больше одной редакции).
- Индексы по полям payload для фильтров: `vector_store.py:47-54`.

## 3. Гибридный поиск

**Код:** `search()` — `app/services/rag/retriever.py:118-198`; Qdrant-обёртка — `app/services/rag/vector_store.py`.

- **Метрика:** dense — `Distance.COSINE` (`vector_store.py:43`); sparse — скалярное произведение весов (стандарт sparse-векторов Qdrant), без IDF-модификатора (`vector_store.py:44-45`).
- **Сколько запросов:** до 8 формулировок (`normalizer.py` `to_search_request`, `queries[:8]`). На каждую — 2 отдельных запроса в Qdrant: dense и sparse, по **30** кандидатов (`per_channel=30`, `retriever.py:36, 128-133`). Итого до 16 списков.
- **Точные ссылки:** если в вопросе есть «ст. 42 п. 8», через `scroll` по полям `article/point/act_code` берутся эти пункты (`retriever.py:70-115`) — отдельный список с весом 2,0 (`EXACT_WEIGHT`), такие пункты закрепляются (`pinned`).
- **Фильтры** (`vector_store.py:83-137`):
  - редакция (`time_filter`, см. п. 4);
  - список актов — только если задан;
  - фильтра по языку нет: ищется и ru, и kk.
- **RRF** считается в нашем коде на Python, не встроенной функцией Qdrant (`retriever.py:139-161`):
  - формула `rrf += weight / (60 + rank)`, `RRF_K=60`;
  - складывается по **юридической единице**: ru и kk версии одного пункта суммируются;
  - внутри одного списка единица учитывается один раз.
- После RRF — множитель иерархии (п. 5), сортировка. В пул попадают все найденные единицы (в замерах — десятки).

## 4. Редакция на дату события

**Код:** `app/services/lawyer/editions.py:33-62`, `vector_store.time_filter` (`vector_store.py:83-109`), вызов — `app/services/lawyer/pipeline.py:46-57`.

1. Если `event_date` есть — `resolve_editions(as_of)` берёт из PostgreSQL акты, у которых больше одной редакции.
2. Для каждого такого акта `_choose`:
   - есть редакция, где `valid_from ≤ дата < valid_to` → она, `exact=True`;
   - нет → ближайшая более ранняя загруженная (или самая ранняя), `exact=False`.
3. В Qdrant уходит фильтр «ИЛИ» из трёх частей:
   - акты без истории — только `is_current=true`;
   - для каждого акта с историей — точки его выбранной редакции по `valid_from_i ≤ день < valid_to_i`;
   - остальные акты с историей — по самой дате события.
4. Если `exact=False`, в промпт добавляется `<edition_note>` с просьбой сказать об этом в ответе и посоветовать сверить норму на adilet (`generator.py:62-67`).
5. **Даты нет** → фильтр только `is_current=true`, то есть действующие редакции (`vector_store.py:90-91`).

Ограничение: история загружена только у 4 актов (ZHO, RULES_MGMT, RULES_DECISIONS, METHOD_BUDGET). У остальных 11 при любой дате ищется действующая редакция.

## 5. Реранкер и приоритет закона над правилами

**Реранкер** — `Reranker.score`, `app/services/rag/models.py:88-109`; вызов — `retriever.py:172-187`.
- Модель `BAAI/bge-reranker-v2-m3`, cross-encoder.
- Берутся 20 лучших по RRF (`rerank_pool=20`, `config.py:23`) плюс до 10 закреплённых точных ссылок из хвоста.
- Каждая пара `[вопрос, текст фрагмента]` подаётся в модель целиком, обрезка до 384 токенов (`rerank_max_length`), пачками по 10. Выход — логит → `sigmoid` → оценка от 0 до 1.
- Запрос для реранкера: `normalized_ru`, если разбор делал LLM, иначе исходный текст (`normalizer.py` `to_search_request`).
- Выключается настройкой `RERANK_ENABLED=false`.

**Приоритет закона** — `retriever.py:85-96, 163-168, 185`.
- Уровень акта берётся из `ingest/sources.toml` (`hierarchy_level`: 1 Конституция, 2 кодекс, 3 закон, 4 постановление, 5 приказ / правила).
- `LEVEL_WEIGHTS = {5: 0.85}`: оценка приказов и правил умножается на 0,85 — и после RRF, и после реранкера. Закреплённые точные ссылки не штрафуются.
- Множитель мягкий: правило всё равно выше, если оно заметно точнее отвечает на вопрос.
- Замер на 186 контрольных вопросах: нужная норма первой — 58% без реранкера и без приоритета → 67% с обоими.

## 6. Как выбираются 8 основных и до 4 дополнительных норм

**8 основных** — `diversify()`, `retriever.py:201-222`, `top_k=8` (`pipeline.py:24, 46`).
- Идём по отсортированному пулу и берём единицы, пока не наберём 8.
- Не больше 2 единиц одного пункта (`per_point=2`) и 3 одной статьи (`per_article=3`). Лишние откладываются и добираются, только если не хватило.
- Закреплённые точные ссылки ограничения не касаются. Если названная в вопросе статья не попала в 8, она заменяет последнюю (`retriever.py:190-193`).

**До 4 дополнительных** — `expand_xrefs()`, `retriever.py:264-288`; распознавание — `app/services/rag/xrefs.py`.
- Из **5 лучших** результатов берётся русский текст (без строки «хлебных крошек»).
- Регулярными выражениями ищутся отсылки: «статьёй 10», «пункта 3 статьи 42», «настоящего Закона», «осы Заңның 10-бабы»; названия других актов распознаются по словарю `ACT_HINTS` (`refs.py`).
- Пропускаются: уже найденная статья, ссылка на саму себя, повторы.
- Если указан пункт — берётся он. Если только статья — ближайший к вопросу пункт этой статьи по dense-вектору (`_resolve_xref`, `retriever.py:241-261`).
- С тем же фильтром редакции, максимум 4. В контексте у них `role="cross_reference" referenced_from="…"`.

## 7. Как собирается запрос к LLM для ответа

**Код:** `build_context` — `app/services/lawyer/context.py:60-86`; `build_user_content` — `app/services/lawyer/generator.py:54-74`; вызов — `generate_llm` (`generator.py:77-109`) или `generate_claude_code` (`generator.py:183-204`).

**Системный промпт:** файл `app/prompts/lawyer.md` (11,4 тыс. знаков).
- В режиме API помечен для кэширования (`cache_control: ephemeral`).
- В режиме `claude_code` к нему дописывается JSON-схема ответа.

**Сообщение пользователя — блоки строго в таком порядке:**
1. `<available_templates>` — 6 шаблонов документов (`schema.py:10-17`).
2. `<context>` — 8–12 фрагментов. У каждого `<chunk chunk_id act article point version_date edition level url [role referenced_from]>`, внутри «хлебные крошки» и текст.
3. `<normalized>` — весь результат разбора вопроса в JSON, плюс выбранные редакции.
4. `<event_date precision="…">`.
5. `<edition_note>` — только если точной редакции на дату нет.
6. `<user_role>` — если указана роль (собственник, ОСИ, УК, юрист).
7. `<previous_turns>` — последние 6 сообщений дела.
8. `<user_message>` — исходный текст вопроса.

**Параметры в режиме API:**
- модель `claude-opus-5-5`, `max_tokens=64000`;
- `thinking: adaptive`, `effort: high`;
- ответ строго по `LAWYER_SCHEMA`, поток (стриминг);
- server-side fallback при отказе.

**Поля ответа** (`schema.py:78+`): `verdict`, `verdict_text`, `summary`, `legal_answer`, `assumptions`, `legal_basis[{chunk_id, act, article, point, quote, explanation}]`, `responsibility`, `assessment{position, reasoning, risks}`, `action_plan`, `documents`, `clarifying_questions`, `not_found`, `disclaimer`.

**В режиме `claude_code`:**
- одна попытка, без стриминга;
- если JSON не прошёл схему — одна повторная попытка с текстом ошибки (`generator.py:191-200`).

## 8. Проверка ссылок и что бывает при ошибке

**Код:** `verify_answer` — `app/services/lawyer/verify.py:57-102`; флаг — `Verification.needs_review` (`verify.py:24-34`).

1. Каждое правовое основание ищется в контексте по `chunk_id`, а если его нет — по паре (статья, пункт).
   - Не найдено → **основание удаляется**, id попадает в `removed_citations`.
   - Найдено → акт, статья и пункт **перезаписываются данными из базы**.
2. **Цитата** сверяется с текстом пункта (ru и kk):
   - перед сравнением: нижний регистр, ё→е, без кавычек, схлопнутые пробелы;
   - цитата с «…» проверяется по частям, каждая часть не короче 10 знаков.
   - Не совпала → заменяется настоящим текстом пункта (до 400 знаков), `quote_verified=false`, растёт счётчик `replaced_quotes`.
3. Ссылки в разделах «ответственность» и «план действий» на чужие id удаляются.
4. Номера статей в свободном тексте ответа (`extract_refs`) — если статьи нет среди найденных, она попадает в `unverified_refs`.
5. Любое из трёх нарушений → `needs_review=true`. Ответ всё равно показывается, но сохраняется с этим флагом и попадает в очередь юриста в админке (`GET /v1/admin/review`).

**Если сама модель упала** (отказ, обрезка, сеть, невалидный JSON) — `pipeline.py:69-82`:
- жителю уходит событие `notice: llm_failed`;
- вместо толкования показывается демо-ответ: 3 найденные нормы дословно (`generate_demo`).

## 9. Изменение закона при повторной загрузке, судьба старых векторов

**Код:** `check_updates` — `app/services/admin/tasks.py:81-102`; `load_act` — `ingest/loader.py:52-102`; `index_version` — `ingest/indexer.py`; `refresh_payloads` — `tasks.py:50-62`.

1. **Есть ли новая редакция:** с вкладки «История» Adilet берётся дата действующей редакции (`fetch_versions`). Если в базе действующая редакция не старше её — ничего не делаем.
2. Иначе скачиваем и разбираем текст, считаем **SHA-256 от HTML ru + kk** (`loader.py:26-31`).
   - Хэш совпал с текущей редакцией → новая редакция не создаётся.
   - Не совпал → старая получает `is_current=false, valid_to=дата новой`, новая создаётся с `is_current=true`, единицы пишутся заново.
3. **Индексация новой редакции** (`indexer.py:42-107`):
   - фрагменты нарезаются заново;
   - для каждого считается `content_sha`;
   - если такой текст уже есть в Qdrant (из прошлой редакции), вектор **копируется, а не считается заново** (`lookup_vectors`, `vector_store.py:112-127`);
   - точки этой редакции в Qdrant сначала удаляются, потом записываются заново.
4. **Старые векторы не удаляются:**
   - `refresh_payloads` переписывает у точек всех редакций `is_current`, `valid_from/to`, `temporal`;
   - старая редакция перестаёт попадать в обычный поиск, но остаётся для вопросов с датой события в прошлом.
5. **Удаление** — только вручную, кнопкой (`delete_version`, `tasks.py:141-166`):
   - действующую редакцию удалить нельзя;
   - редакцию, на которую ссылаются сохранённые ответы, удалить нельзя;
   - иначе удаляются точки в Qdrant по `version_id`, затем фрагменты и единицы в PostgreSQL.
6. **Фрагменты в PostgreSQL** при переиндексации обновляются на месте. Лишние удаляются, только если на них не ссылаются цитаты сохранённых чатов (`indexer.py:51-73`).

**Не реализовано:** автоматическая ежедневная проверка — запуск только из админки (`POST /v1/admin/acts/check-updates`) или командой `python -m ingest`.

# Сценарий выступления

## Часть 1. От открытия сайта до ответа

**1. Житель открывает сайт.** Сайт на Next.js, на русском и казахском. Он пишет в чат, например: «соседи сверху затопили квартиру, что делать».

**2. Вопрос уходит на сервер.** Сайт отправляет `POST /v1/chat`: текст, роль (собственник, ОСИ, УК или юрист) и историю этого дела. Ответ сервер шлёт потоком событий: «понимаю вопрос», «ищу нормы», найденные нормы, текст ответа. Каждые 15 секунд идёт служебный пинг, чтобы соединение не оборвалось, пока модель думает.

**3. Разбор вопроса.** Нужно понять язык, перевести сленг в юридические термины, найти упомянутые статьи и дату события.
- **С API-ключом** это делает Claude по отдельной короткой инструкции. Он возвращает JSON: язык, вопрос на ru и kk, категорию из 15, стороны, факты, нормы, 3–5 поисковых формулировок и дату.
- **Сейчас в демо** это делает код без модели: язык — по казахским буквам и словам, сленг — по словарю ЖКХ, латиница переводится в кириллицу. Категорию этот путь не определяет.
- **Дата** в обоих случаях дополнительно ищется регулярными выражениями. Даты реквизитов вида «Закон от …» не считаются; «в этом году» означает действующую редакцию.

**4. Выбор редакции.**
- Если дата события есть, по каждому из 4 актов с историей выбираем редакцию, действовавшую в тот день.
- Если точной нет — ближайшую раннюю, и модель обязана сказать об этом в ответе.
- Без даты ищем только по действующим редакциям.

**5. Векторы вопроса.** BGE-M3 переводит каждую из (до 8) формулировок в два вектора:
- смысловой: 1024 числа;
- словесный: вес каждого слова.

Законы переведены в векторы той же моделью заранее, поэтому их можно сравнивать.

**6. Поиск в Qdrant.** На каждую формулировку два запроса, по 30 кандидатов: по смыслу (косинус) и по словам. Плюс точные попадания, если житель сам назвал статью. Все списки объединяем методом RRF: чем выше место в каждом списке, тем больше очков. Русская и казахская версии одного пункта складываются. Приказы и правила получают множитель 0,85, чтобы при равенстве первым шёл закон.

**7. Переоценка.** 20 лучших кандидатов реранкер читает вместе с вопросом и ставит каждому оценку от 0 до 1. После этого снова действует приоритет закона.

**8. Отбор норм.**
- Берём 8 лучших: не больше 2 фрагментов одного пункта и 3 одной статьи.
- Из 5 лучших ищем отсылки вида «в соответствии со статьёй 10» и добавляем до 4 таких норм.
- Эти нормы сразу показываются жителю в панели «Источники».

**9. Ответ.** Модель получает инструкцию юриста и одно сообщение из блоков:
- шаблоны документов;
- нормы с номерами, редакцией и ссылкой на Adilet;
- результат разбора;
- дату события;
- роль;
- последние 6 сообщений дела;
- сам вопрос.

Модель обязана отвечать только по этим нормам и вернуть JSON строгой формы: вердикт, простой ответ, ответ для юриста, основания с цитатами, план действий, документы.

**10. Проверка ссылок.** Ответу модели на слово не верим.
- Основание, которого нет среди найденных норм, удаляется.
- Номер статьи и название акта берутся из базы.
- Цитата сравнивается с текстом пункта. Если не совпала, подставляется настоящий текст с отметкой «не подтверждена».
- Если что-то исправили, ответ помечается «нужна проверка» и попадает юристу в админку.

**11. Сохранение и показ.** В базу пишутся: вопрос, разбор, ответ, процитированные нормы, расход токенов, время каждого этапа и какие кандидаты нашёл поиск. Житель видит ответ, источники и редакцию.

**12. Если модель не ответила** (отказ, сеть, плохой JSON) — житель видит предупреждение и три найденные нормы дословно.

## Часть 2. Как обновляются законы

**1. Список актов** — файл `ingest/sources.toml`: код, номер на Adilet, название, уровень (Конституция, кодекс, закон, приказ). Сейчас 15 актов.

**2. Проверка обновлений.** Админ нажимает «Проверить обновления». Это ручной запуск: автоматического ежедневного пока нет.
- Система открывает вкладку «История» документа на Adilet и берёт дату действующей редакции.
- Если у нас она не старше — ничего не делаем.

**3. Скачивание.** Adilet — одностраничное приложение, текст появляется только после выполнения JavaScript. Поэтому страницу открывает браузер без окна (Playwright), отдельно на русском и казахском. Один запрос за раз, с паузой и кэшем.

**4. Разбор.** Код восстанавливает структуру: раздел → глава → статья → пункт → подпункт. У каждой единицы адрес вида `art42/p3/sp1`, одинаковый на двух языках, — по нему склеиваются ru и kk.

**5. Новая редакция или нет.**
- Считаем SHA-256 от текста страницы. Совпал с текущим — ничего не создаём.
- Новый — прошлая редакция получает дату окончания и перестаёт быть действующей, новая становится действующей. Старую не удаляем.

**6. Векторизация.**
- Новая редакция режется на фрагменты по пунктам.
- Если текст пункта не изменился с прошлой редакции, вектор копируем по хэшу; BGE-M3 считает только изменённые.
- Векторы и метки (акт, статья, пункт, язык, срок действия) пишутся в Qdrant.
- У точек старой редакции переписываются флаги: в обычный поиск она больше не попадает, но остаётся для вопросов о прошлых датах.

**7. Удаление** старой редакции — только вручную. Нельзя удалить действующую редакцию и редакцию, на которую ссылаются сохранённые ответы.

**8. Проверка качества** — кнопка в админке. Прогоняет 186 контрольных вопросов и показывает, на каком месте оказалась нужная норма. Сейчас: первая в 67% случаев, в первой десятке — в 91%.

## На какие вопросы мы честно отвечаем «пока нет»

- Ежедневная автопроверка Adilet — нет, только кнопка.
- История редакций — только у 4 актов из 15.
- Gemini, отдельная дешёвая модель для разбора, свой LLM — нет.
- В демо разбор вопроса делается без LLM, категория не определяется.
- Время работы моделей на обычном CPU-сервере не измерено: замеры сделаны на Mac (Apple GPU, fp16).
